# Releases

## v0.1.0

- Establish the repository and shared Base development tooling.
- Add the HTTP/1.1 load generator, generalized from the hello benchmark's fixed-rate client: a closed loop for maximum throughput, reported as service time, and an open loop on an absolute schedule with latency from each request's planned send time, both with optional pipelining. Workers are pinned, busy-polling epoll threads that share nothing while running.
- Validate every response: framing by length, chunks, or close, the status, the expected body (by default the preflight response's), required headers, or the exact whole response. Count invalid responses by reason and failed requests by kind next to the successes, and reconnect after failures; every planned request has exactly one outcome.
- Report HdrHistogram-style distributions merged exactly across workers, per-interval statistics, fairness across connections and workers, and client saturation, in one `base-benchmark` process record. Its operations are the valid responses only, as `base-benchmark` requires of a driver, and its parameters do not depend on the server's address.
- Judge client saturation by busy time over `--busy-limit` (0.8), by each worker's 99th percentile *schedule lag*, how late it reached each due request whether or not its connection had room, over `--schedule-lag-limit` (50 µs), and in rate mode by the requests planned in the window that the workers reached only after it, over `--shortfall-limit` (0.001). Report the requests planned in the window but not sent in it as a shortfall, split into the client's part, requests not reached in it, and the connections' part, requests reached in it while their connections awaited responses or reconnected, each clamped so that they add up to the shortfall. The connections' part is reported as requests held back rather than as the client's saturation: by the server only when the client kept its schedule, with no worker later than the schedule lag limit, and otherwise by the connections, with how many requests they may have outstanding and the round trip under which that many carry the offered rate. Report each pinned worker's CPU time in software interrupts, which its thread's CPU time leaves out.
- Report connections the server starved, as Puma does with more keep-alive connections than threads: a connection none of whose requests of the measured period the server answered, or one the server left without a response, with a request outstanding or due, for longer than `--starved-limit` (0.25) of the window, across its timeouts and reconnections and on into the drain, so that a connection served for a while and then starved is reported too. Starvation only in the drain, of a connection whose spans were within the limit in the window, is stated apart, and the reason says when the limit is shorter than the median round trip, so that even a fair server exceeds it. The summary states the starved connections, the longest starved span, and the longest wait for a response before any distribution, and the record has `connections_starved`, `connections_starved_fraction`, `starved_span_max`, and `response_wait_max`, lower-is-better, with the details in the extension's `starvation`. `--fail-on starved` exits without a record when any connection was starved in the window. The closed loop's summary states the outcomes of the requests in flight at the window's end, which it drains rather than abandons.
- Read each response with one `recvfrom`, by not reading again after a read shorter than the buffer offered on an edge-triggered socket, except when the event reported the peer's close.
- Record the evaluation on the measuring host hana in `results/2026-11-09-hana`.
- Act as the driver role of `base-benchmark` 0.4's multi-process scenarios, and depend on `base-benchmark` 0.4 instead of 0.2. Under the runner, which sets `BASE_BENCHMARK_CONTROL=stdio`, the controller marks the measured window with `base_benchmark::Window`, on stdout before the record: it marks the start and waits for the runner's acknowledgement before the window starts, so that the runner's snapshot of the services precedes every request planned in the window in rate mode, and every outcome the closed loop's window counts, and marks the stop after the services' work for every request the window counts: in rate mode once every request has an outcome, so that requests planned in the window but sent or served after it, as when the server falls behind, are in the services' window, and in the closed loop when the window ends. With `--window-lead` (100 ms) at least as long as the warmup, the start is marked once every worker has connected, and the load starts only once it is acknowledged; otherwise it is marked that long before the window, and an acknowledgement after the window's start fails the run, without a record. Outside the runner nothing changes, and stdin is never read; an unsupported `BASE_BENCHMARK_CONTROL` fails the run. `run_with_window` marks a run with a given `Window`, and `run` marks none. The record's extension has `window`, when the markers were sent and acknowledged and whether the stop followed the drain, or null, and the summary a line saying the same. Scenarios name the record's `responses_invalid` as the driver's `invalid-responses`.
- Record the window markers' evaluation with the runner on aiko in `results/2026-11-09-aiko-window`.
